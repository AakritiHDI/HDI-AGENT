What is SAP HANA HDI?

HDI = HANA Deployment Infrastructure

HDI is SAP HANA's container-based deployment system for managing database artifacts. Instead of running raw DDL directly, you define artifacts in design-time files and let HDI compile and activate them.

ConceptDescriptionAnalogy
ContainerAn isolated namespace (schema) in HANA — all artifacts live hereA private project folder
Work AreaStaging area — files written but not yet activatedDraft / staging branch
Runtime SchemaLive activated objects visible in DBX (tables, views, procs)Production database
.hdiconfigPlugin registry — maps file extensions to HANA build pluginspackage.json / build config
DI.WRITEStage a design-time file in the work areagit add
DI.MAKECompile and activate staged files → creates runtime objectsgit push / CI build
DI.DELETERemove a file from work area and undeploy the runtime objectgit rm + drop table
Key Principle: DI.WRITE stages files. DI.MAKE activates them. Without MAKE, nothing appears in the database.
HDI Container Lifecycle — From Scratch
Step 1 — CREATE CONTAINER
CALL _SYS_DI.CREATE_CONTAINER('AGENTHDI_CONTAINER', ...)
→ HANA creates schema "AGENTHDI_CONTAINER"
→ Technical users created: AGENTHDI_CONTAINER#OO (Object Owner), AGENTHDI_CONTAINER#DI (DI User)
▼
Step 2 — GRANT DI API PRIVILEGES
GRANT_CONTAINER_API_PRIVILEGES → HDI_USER gets WRITE / MAKE / DELETE / LIST access
▼
Step 3 — WRITE .hdiconfig to Work Area
DI.WRITE(".hdiconfig", '{"file_suffixes": {"hdbtable": {"plugin_name": "com.sap.hana.di.table"}, ...}}')
→ Registers ALL build plugins for this container
▼
Step 4 — WRITE Artifact Files to Work Area
DI.WRITE("src/EMPLOYEE.hdbtable", 'COLUMN TABLE "EMPLOYEE" (...)')
→ File is staged — NOT yet active in the database
▼
Step 5 — DI.MAKE (Deploy / Activate)
DI.MAKE(DEPLOY=[".hdiconfig", "src/EMPLOYEE.hdbtable"])
→ HANA compiles files using registered plugins
→ CREATE COLUMN TABLE "EMPLOYEE" executed in schema AGENTHDI_CONTAINER
▼
Step 6 — GRANT Schema Privileges
GRANT SELECT, EXECUTE ON SCHEMA "AGENTHDI_CONTAINER" TO HDI_USER
→ Users can now query the table in DBX

Deep Explanation: HDI Container & Artifact Deployment

Understanding from First Principles

1. What is a Container?

An HDI container is an isolated, self-contained database namespace within SAP HANA. Think of it as a tenant within the database. Every object (table, view, procedure, library) created inside the container lives in the container's own runtime schema — completely separated from other schemas.

When you create a container named AGENTHDI_CONTAINER, HANA automatically:

  • Creates a schema with the same name
  • Creates technical users: AGENTHDI_CONTAINER#OO (owns all objects) and AGENTHDI_CONTAINER#DI (performs DI operations)
  • Sets up the DI API: a set of stored procedures (WRITE, MAKE, DELETE, LIST) accessible under AGENTHDI_CONTAINER#DI

2. What is the .hdiconfig File?

The .hdiconfig file is the plugin registry for the container. It is a JSON file that maps each file extension to a build plugin: 

{
  "file_suffixes": {
    "hdbtable":           { "plugin_name": "com.sap.hana.di.table" },
    "hdbview":            { "plugin_name": "com.sap.hana.di.view" },
    "hdbprocedure":       { "plugin_name": "com.sap.hana.di.procedure" },
    "hdbcalculationview": { "plugin_name": "com.sap.hana.di.calculationview" },
    "hdblibrary":         { "plugin_name": "com.sap.hana.di.library" }
  }
}

Without .hdiconfig, DI.MAKE cannot compile any artifact. The HDI system doesn't know what plugin to use for a given file extension.

In our container, .hdiconfig is placed at the root level. But HANA also checks for a src/.hdiconfig (directory-level config) that takes precedence for files placed under src/. This distinction caused the library deployment bug: the old src/.hdiconfig was missing the hdblibrary plugin.

3. The Work Area vs Runtime Schema

HDI uses a two-phase model:

Work Area (Staging)Runtime Schema (Active)
Files written via DI.WRITE Objects created via DI.MAKE
Not visible in SYS catalog (SYS.TABLES, SYS.VIEWS) Fully visible in SYS catalog and DBX
Design-time files (.hdbtable, .hdbview DDL) Runtime objects (actual TABLE, VIEW objects)
Survives restarts, accessible via DI.LIST Accessible via SQL SELECT, CALL, etc.
After MAKE: file is removed from staging area Object remains until explicitly undeployed
What Happens During DI.MAKE?

When DI.MAKE is called with a list of files to deploy, HANA performs these internal steps:

1. Prepare the Make Transaction
Locks the container for consistent state
▼
2. Validate File Extensions vs .hdiconfig Plugins
For each file in DEPLOY list: find the registered plugin in .hdiconfig
❌ If plugin not found → ERROR: "Configuration does not define a build plugin for file suffix X"
▼
3. Build Dependency Graph
HANA resolves dependencies between artifacts (e.g. a view depends on a table)
❌ If dependency missing → ERROR: "the file requires db://TYPE which is not provided by any file"
▼
4. Precompile
Parse and validate the DDL syntax of each artifact
▼
5. Execute DDL
Run the equivalent of CREATE TABLE / CREATE VIEW / CREATE PROCEDURE
Objects land in the container's runtime schema owned by #OO user
▼
6. Return rc (return code) and M_MESSAGES
rc=0: success | rc=1: success with warnings | rc<0 or rc>1: error
M_MESSAGES table contains detailed INFO / WARNING / ERROR messages per file
Important: HANA sometimes returns rc=0 but creates nothing. This happens when .hdiconfig is not in the MAKE context for certain plugin types (CVs, libraries). HDI-Agent handles this by always including .hdiconfig + src/.hdiconfig in the MAKE for these artifact types.

How to Debug a Failed MAKE

-- Query M_MESSAGES after a failed deploy (use the REQUEST_ID from MAKE call):
SELECT SEVERITY, MESSAGE_CODE, MESSAGE, PATH
FROM "AGENTHDI_CONTAINER#DI"."M_MESSAGES"
WHERE REQUEST_ID = <request_id>
ORDER BY ROW_ID;

-- HDI-Agent logs this automatically at INFO level:
-- LIB_VERIFY | AGENTHDI_CONTAINER | MATH_UTILS | M_MESSAGES (req=157685): [...]
